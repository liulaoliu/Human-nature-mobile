### 🟡 W1 — 「测试连接」测的是上一次保存的旧配置，不是输入框里刚打的新 key/地址（R6 领域模型失真 / 接线错误）

- **Symptom**：用户在 AI 跑批页改完 `baseUrl` / `apiKey`，**不点「保存到本机」**直接点「测试连接」，页面拿去发请求的配置仍是上一次 `updateConfig` 存进 `_config` 的旧值；用户会看到「连接正常」却并不是用刚填的新 key 测的，或者反过来新地址明明不通却报旧地址通。
- **Source**：`I:\Examples\dlaoshi_app\lib\views\ai_batch_page.dart:66-84`

  ```dart
  Future<void> _test(AiBatchViewModel vm) async {
    final config = _collect(vm);            // :67 从输入框拼出新 config
    if (!config.hasApiKey) { ... }          // :68 只用新 config 判了个空
    ...
    final reply = await vm.testConnection(); // :76 却调无参版本，读的是 vm._config
  }
  ```

  对照 `I:\Examples\dlaoshi_app\lib\viewmodels\ai_batch_view_model.dart:133-134`：`Future<AiReply> testConnection() => complete(_config, '请只回复两个汉字：正常');` 只吃字段 `_config`。而 `_run` / `_resume`（`ai_batch_page.dart:86-94`）都先 `await _saveConfigSilently(vm)`（`:96-99`，`if (config != vm.config) await vm.updateConfig(config)`）才跑 —— 唯独 `_test` 漏了这一步。拼接出来的新 `config` 在 `:67` 之后就再没被用到。
- **Consequence**：这是本次审查里**唯一一个用户能直接踩到、且会误导判断**的功能缺陷。「测试连接」的意义就是验证「我刚填的这串值」，结果验证的是陈旧值；用户据此以为新 key 可用，随后点「开始跑批」时 `_saveConfigSilently` 才把新值写进去，前后行为不一致。
- **Remedy**：`_test` 里在 `vm.testConnection()` 之前 `await vm.updateConfig(config)`（或让 `testConnection(AiConfig config)` 接参、页面直接把 `_collect(vm)` 传进去），保证「测什么 = 框里是什么」。补一条 widget 测试：改输入框 → 点测试连接 → 断言假 `complete` 收到的 config 是新值。

### 🟡 W2 — 写路径绕过了 `normalizeAiConfig`，`_completionsUri` 也不查 scheme（守卫「只读不写」）

- **Symptom**：项目专门写了 `normalizeAiConfig` 用来洗外部设置（去尾斜杠、验 http(s) + host、clamp 温度），但它**只在 `PrefsStore.loadAiConfig()` 读路径生效**；用户在输入框里手填的值经 `_collect` → `vm.updateConfig` 直接落库和发请求，完全不过这道守卫。
- **Source**：`I:\Examples\dlaoshi_app\lib\core\ai_config.dart:85-103`（`normalizeAiConfig`）、`:115-127`（`_cleanBaseUrl` 里 `if (uri.scheme != 'http' && uri.scheme != 'https') return defaultAiBaseUrl;`）只被 `I:\Examples\dlaoshi_app\lib\data\prefs_store.dart:187-195` 的 `loadAiConfig()` 调用。写路径 `I:\Examples\dlaoshi_app\lib\viewmodels\ai_batch_view_model.dart:125-130`：

  ```dart
  Future<void> updateConfig(AiConfig config) async {
    _config = config;                 // 未 normalize
    _error = '';
    await _store.saveAiConfig(config);
    _notify();
  }
  ```

  而 `I:\Examples\dlaoshi_app\lib\services\ai_client.dart:157-161` 的 `_completionsUri` 只挡 `host.isEmpty`：

  ```dart
  Uri? _completionsUri(String baseUrl) {
    final uri = Uri.tryParse('$baseUrl/chat/completions');
    if (uri == null || uri.host.isEmpty) return null;   // 不查 scheme
    return uri;
  }
  ```

  `ftp://foo` 之类会解析出非空 host 直接进 `_inner.post`。
- **Consequence**：同一个 `AiConfig` 对象，「从磁盘读回来」和「用户刚输入」走两套校验强度。坏地址 / 越界温度 / 带尾斜杠的 baseUrl 在本次会话内不会被纠正，会以一个含糊的「网络异常」（`ai_client.dart:139-149`）呈现，而不是清晰的「服务地址不合法」。守卫函数存在却被绕过，本身也是 Information Leakage 式的一致性缺口。不是安全灾难（http 客户端会拒绝非 http scheme），但属于「写了防御却没接上」。
- **Remedy**：`updateConfig` 里先 `_config = normalizeAiConfig(aiConfigToJson(config))` 再存；`_completionsUri` 补 `if (uri.scheme != 'http' && uri.scheme != 'https') return null;`。把 `normalizeAiConfig` 的调用点从「仅读」扩成「读写都过」，让 `test/core/ai_config_test.dart` 的用例同时覆盖写路径。

### 🟡 W3 — `refresh()` 不清 `_doneIds`/`_failedIds`，下拉刷新后进度文案与实际待办对不上（T2 状态分叉）

- **Symptom**：跑完一轮后下拉刷新（或 `bootstrap()` 二次调用），`_jobs` 按词库重算、`_index` 归零，但已完成 / 失败标记集合被刻意保留，`progressText` 和 `allDone` 仍拿旧集合长度算，会显示「完成 3」而当前其实只剩 2 块。
- **Source**：`I:\Examples\dlaoshi_app\lib\viewmodels\ai_batch_view_model.dart:106-122`

  ```dart
  /// 重建任务列表（保留本次会话已完成 / 失败的标记，供界面显示）。
  Future<void> refresh() async {
    ...
    _jobs = buildAiLookupJobs(library);   // :113 重算
    _index = 0;                           // :114
    _phase = AiBatchPhase.idle;           // :115
    // _doneIds / _failedIds 不清
  }
  ```

  但 `:84 bool get allDone => _jobs.isNotEmpty && _doneIds.length == _jobs.length;` 与 `:92-96 progressText` 的 `' · 完成 ${_doneIds.length} · 失败 ${_failedIds.length}'` 都基于未清的集合。任务 id 是 `'lookup-${aiFingerprint(words.join('\n'))}'`（`I:\Examples\dlaoshi_app\lib\core\ai_jobs.dart:101-123`），词库变化后 `words` 组合会变，旧 id 与新 `_jobs` 可能对不上。
- **Consequence**：`run()` 的跳过逻辑（`:161 if (_doneIds.contains(job.id))`）用旧集合判断，若新 id 恰好撞上旧 doneId 会被误跳过；进度条 / 「完成 N」也给用户错误预期。注释说「保留供界面显示」，但界面显示用的正是这些没被重算脏的计数。
- **Remedy**：`refresh()` 里 `_doneIds.clear()` / `_failedIds.clear()`（若确实要「本次会话不重跑已完成块」，应改成按新 `_jobs` 的 id 取交集，而不是无条件保留）。补一条测试：造 3 块跑完 → 改词库让待办变成 2 块 → `refresh()` → 断言 `progressText` 的「完成」≤ 2、`allDone` 不会被旧计数误判。

### 🟡 W4 — `_runOne` 不核对模型回的词是不是本块请求的，幻觉词会直接写进词库（数据完整性）

- **Symptom**：每块查词只把 `job.prompt` 发给模型，回来后 `parseAnalysis(reply.text).words` 全量喂给 `applyWordAnalysis` 落库，**没有和本块的 `job.words` 做比对**。
- **Source**：`I:\Examples\dlaoshi_app\lib\viewmodels\ai_batch_view_model.dart:220-252`

  ```dart

  final parsed = parseAnalysis(reply.text);             // :235
  if (parsed.words.isEmpty) { ... }                    // :236 只判「有没有」
  final library = await _vocabRepo.load() ?? const VocabLibrary();
  await _vocabRepo.save(applyWordAnalysis(library, parsed.words));  // :242-243 全量落
  ```

  `applyWordAnalysis`（`I:\Examples\dlaoshi_app\lib\core\vocab\analysis.dart:248`）对没见过的 lemma 会新建 `VocabItem(id: 'vocab:$lemma', status: queried, ...)`。`AiJob` 带 `words` 字段（`I:\Examples\dlaoshi_app\lib\core\ai_jobs.dart`），本可用于校验，但没用上。
- **Consequence**：模型偶尔多回 / 拼错一个词，就会在用户词库里凭空多出一条词条；跑批是批量、少人盯的，这种脏数据会静默累积且难以回溯是哪一块带进来的。与「词库只收我选的词」这一产品口径冲突。
- **Remedy**：落库前把 `parsed.words` 按 `job.words`（忽略大小写 / 走 `lemma`）过滤，只保留请求过的；被丢掉的数量记进 `AiBatchOutcome` 或在 `_notice` 里提示「本块有 N 个词没对上，已跳过」。补一条测试：假 `complete` 返回一个含请求外单词的表格 → 断言词库里没有多出该词条。

### 🟢 S3 — `resume()` 在 `done` 状态仍会走一遍 `run()` 并复述「跑完了」（状态机小尾巴）

- **Symptom**：`resume()` 只挡 `running`，跑完（`done`）后再点「继续」，会重新进入 `run()`、把 `_phase` 重置成 `running` 再置回 `done`，`_notice` 复述一次「跑完了」。
- **Source**：`I:\Examples\dlaoshi_app\lib\viewmodels\ai_batch_view_model.dart:198-201` `Future<void> resume() async { if (_phase == AiBatchPhase.running) return; await run(); }`，配合 `run()` 的 `:141-187`（`_index` 已在 `_jobs.length` 时 while 不进循环，但收尾文案照发）。
- **Consequence**：无数据损失、`_doneIds` 会让块被跳过，只是「继续」按钮在已完成态仍可点且会给一条多余的完成提示，状态机语义不够闭合。
- **Remedy**：`resume()` 开头补 `if (_phase == AiBatchPhase.done) return;`，或在页面层用 `vm.phase` 控制「继续」按钮的可用态。
